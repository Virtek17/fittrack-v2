# FitTrack

Production: https://fittrack-v2-iota.vercel.app · бот: https://t.me/FitTrackv2_bot

Проект Vercel: https://vercel.com/ilyas-projects-012b9832/fittrack-v2. Первый деплой выполнен через Vercel Drop, без привязки Git. Обновления можно загрузить через Drop на странице этого проекта; серверные переменные остаются в настройках Vercel. Пакет исходников не должен содержать `.env.local`, личные отчёты и резервные копии. Серверные ключи находятся в секретных переменных Production; локальные изменения `.env.local` автоматически их не обновляют.

Проверить production: `node --env-file=.env.local scripts/check-deployment.mjs https://fittrack-v2-iota.vercel.app`. Скрипт проверяет доступность, заголовки кеширования, отсутствие ключей в сборке и защиту API. Настроить кнопку бота: `node --env-file=.env.local scripts/configure-bot.mjs https://fittrack-v2-iota.vercel.app --apply` (без `--apply` только проверяет текущее меню).

Mobile-first дневник тренировок и питания на React + TypeScript + Vite, подготовленный для Telegram Mini App.

## Локальный запуск

Нужен Node.js 24+. Выполните `npm install`, затем `npm run dev`. Проверки: `npm test`, `npm run lint`, `npm run build`.

Работают:
- Ручные тренировки: упражнение, отдельные подходы, вес, повторения, дублирование, отметка выполнения.
- Шаблоны с плановыми подходами и повторениями. Плановые строки не становятся выполненными автоматически.
- История с редактированием и удалением. При повторении упражнения показываются подходы последней завершённой тренировки не позднее выбранной даты. При нескольких тренировках в один день используется последняя сохранённая.
- Импорт подробного русскоязычного CSV FatSecret: даты, порции, продукты, приёмы пищи, КБЖУ и дополнительные нутриенты. Поддерживаются UTF-8 и Windows-1251, десятичные запятые, кавычки. Пропуски остаются null. Повторный импорт заменяет целые дни после подтверждения.
- Автосохранение локального черновика, JSON-экспорт и восстановление.
- Проверка Telegram initData на сервере; облачная копия с контролем версии.

В разработке данные сохраняются в localStorage. Это не надёжная долгосрочная база: очистка браузера удаляет локальные записи. Используйте резервные копии или настройте облако. Автосинхронизации и полноценного офлайн-кеширования приложения пока нет. Кнопка синхронизации сохраняет весь дневник; это намеренно простой формат первой версии.

## Vercel + Supabase + Telegram

1. Создайте Supabase-проект. Выполните `supabase/schema.sql` в SQL Editor. Таблица закрыта для anon/authenticated; доступ имеет только серверная service role. Функция сохранения атомарно проверяет ревизию, защищая от параллельной перезаписи.
2. Разместите репозиторий на Vercel как Vite-проект. Build: `npm run build`; output: `dist`. Каталог `api/` содержит Node.js serverless endpoint. Выберите Node.js 24.
3. В настройках Vercel добавьте `TELEGRAM_BOT_TOKEN`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY` по `.env.example`, затем выполните redeploy. Эти значения **не должны** иметь префикс `VITE_` и попадать в клиентский код или Git. Существующий secret key берётся из Supabase API settings.
4. Через BotFather создайте бота и назначьте опубликованный HTTPS-адрес приложения кнопке меню / Mini App. Откройте приложение из бота.
5. Создайте тестовую запись, нажмите «Синхронизировать», откройте Mini App на другом устройстве и загрузите облачную копию. Проверьте изоляцию вторым Telegram-аккаунтом перед общим доступом.

`npm run dev` запускает Vite и локальные API `/api/session` и `/api/state`. Сервер читает секреты из `.env.local`; этот файл исключён из Git. После изменения секретов перезапустите процесс. На Vercel используются одноимённые переменные окружения.

## Авторизация через Telegram

При открытии Mini App сервер проверяет подпись и срок действия `initData`. После проверки `/api/session` создаёт или обновляет запись `app_users` по Telegram ID, затем клиент загружает облачный дневник, если на устройстве нет своих записей. Имя в интерфейсе берётся из проверенного ответа сервера. Телефон, пароль и email не требуются. Сессии без подписи, с подменой пользователя или старше часа отклоняются. Повторный запуск Mini App обновляет данные входа.

Это авторизация приложения через Telegram, без отдельной регистрации в Supabase Auth. Пользователей видно в таблице `app_users`, а не в разделе Authentication → Users. Непосредственный доступ из браузера к обеим таблицам закрыт RLS и правами; все обращения идут через сервер, который извлекает владельца исключительно из проверенной подписи.

Для новых проектов используйте `SUPABASE_SECRET_KEY=sb_secret_...` вместо legacy `SUPABASE_SERVICE_ROLE_KEY` (поддержан как резервный вариант). Секретный ключ отправляется только в серверном заголовке `apikey`. `VITE_TELEGRAM_BOT_URL` — необязательная публичная ссылка `https://t.me/username_bot`, чтобы открыть бота из локального режима. Никогда не добавляйте `VITE_` к токену бота или секретному ключу Supabase.

Облачное сохранение пока запускается кнопкой «Синхронизировать». Автоматически загружаются только данные входа и существующий облачный дневник на пустом устройстве. Локальные записи не перезаписываются без выбора пользователя.

## Хранение и кеширование

`app_users` хранит проверенные Telegram ID и данные профиля. `diaries.data` хранит JSON-снимок всего дневника: тренировки и подходы, шаблоны, питание, справочник упражнений и текущий черновик. `revision` защищает снимок от перезаписи устаревшей версией с другого устройства.

- Интерфейс и изменения дневника сразу работают из памяти React и сохраняются в localStorage. Ключ локальной копии включает Telegram ID; локальный режим браузера имеет отдельный ключ. Переходы по разделам не обращаются к базе.
- При запуске через Telegram сервер проверяет пользователя, затем читает актуальную облачную версию. При ручной синхронизации она проверяется ещё раз. Без изменений повторная запись в базу пропускается.
- `/api/session` и `/api/state` отвечают с `Cache-Control: no-store`; клиент также использует `cache: no-store`. Дневники и данные входа не хранятся в HTTP/CDN-кеше, а сервер проверяет подпись при каждом запросе.
- В `vercel.json` для файлов `/assets/*` настроено `public, max-age=31536000, immutable`. Vite добавляет хеш содержимого в имена JS/CSS; новая сборка получает новые адреса. Для HTML браузер проверяет актуальность перед повторным использованием (`max-age=0, must-revalidate`).

Локальное сохранение не заменяет постоянную базу: очистка хранилища удаляет копию с устройства, а серверная запись позволяет восстановить синхронизированный дневник. Service Worker не используется; загрузка самого приложения без сети не гарантируется. Дополнительный серверный кеш вроде Redis сейчас не нужен. Заголовки CDN надо проверить на опубликованном Vercel-адресе после деплоя.

При первой синхронизации существующая облачная копия предлагается к загрузке с подтверждением замены локальных данных. После загрузки/записи сервер возвращает ревизию. При конфликте сначала экспортируйте локальную копию и загрузите актуальную облачную. Автоматического объединения дневников нет. Telegram-сессия действительна один час; затем нужно переоткрыть Mini App. Идентификатор пользователя для доступа к базе извлекается исключительно из проверенной сервером подписи, а не из тела запроса.

Размер облачного снимка ограничен 2 МБ. Для роста проекта можно мигрировать JSONB-снимки в таблицы workouts, sets и nutrition, не меняя интерфейс. SQL не был выполнен в реальном Supabase автоматически — нужны ваш проект и серверные настройки. Резервное копирование базы следует настроить отдельно.

## Проверка

`npm test` проверяет CSV (итоги без двойного счёта, порции, null/0, кавычки, даты), подходы, историю по ID, валидацию резервной копии и подпись Telegram (подделка, истечение срока, дубли параметров). Живое подключение к Supabase и запуск внутри Telegram проверяются после настройки окружения.

PDF-импорт в эту версию не входит. Данные питания сохраняются без предположения, что каждый день заполнен полностью.

## ИИ-разбор через OpenRouter Free

Локально реализован раздел «Разбор»: цель, необязательный вес тела, период 7/28 дней и дата окончания. Сервер сам строит сводку завершённых подходов и средних нутриентов. Не передаются Telegram ID, имя пользователя, названия тренировок, продукты, порции и имена CSV-файлов. Передаются названия упражнений, даты, цель, вес тела и агрегаты. Отправка требует отдельной галочки согласия в интерфейсе.

Настройка:
1. Создайте API-ключ на https://openrouter.ai/settings/keys и добавьте `OPENROUTER_API_KEY` в `.env.local`. Перезапустите локальный сервер.
2. Выполните `supabase/recommendations.sql` (в текущем проекте таблицы `ai_reports` и `ai_requests` уже проверены через API).
3. После разрешения владельца перенесите ключ в Secret-переменную Production Vercel и загрузите обновлённые исходники в существующий проект. Значение ключа нельзя включать в архив исходников.
4. Протестируйте сначала на вымышленных данных. Реальные сведения отправляются пользователем кнопкой «Получить рекомендации» с согласием.

По умолчанию используется `openrouter/free`. Можно задать `OPENROUTER_MODEL` только с суффиксом `:free`. Платные модели и платные резервные маршруты запрещены; дополнительно максимальные цены входа/выхода установлены в 0. Запрос требует `provider.data_collection=deny`, поддержки JSON-ответа; обязательный ZDR отключён с разрешения владельца. Если бесплатный маршрут не поддерживает эти требования или аккаунту недоступны настройки, запрос завершится ошибкой; ослабления требований автоматически не происходит. В кабинете OpenRouter не включайте добровольное логирование запросов и использование содержимого для улучшения продуктов.

Сводка, модель и версия промпта образуют ключ кеша. Результаты хранятся в закрытой таблице `ai_reports` отдельно для каждого Telegram ID; идентификатор извлекается из проверенной подписи, а не из тела запроса. Сохранённый ответ возвращается без нового запроса к модели. В браузере также хранится последний результат для текущего аккаунта.

Лимиты атомарно проверяются SQL-функцией `claim_ai_report`: 2 новые попытки на пользователя в сутки UTC, 25 на всё приложение в сутки, не чаще одной попытки на приложение в минуту. Неудачные попытки учитываются, потому что они могут расходовать квоту поставщика. Параллельные одинаковые запросы не запускают несколько генераций. Это внутренние ограничения приложения, а не гарантированная квота OpenRouter. Периодический сброс попыток не нужен: лимит считается по датам строк; для длительной эксплуатации можно настроить очистку старого журнала `ai_requests`.

Тесты ИИ используют вымышленные данные и заглушку API: проверяют сводку, отсутствие идентификаторов, согласие, изоляцию кеша, квоты, запрет платных моделей и проверку формата ответа. 24 октября 2026 выполнен успешный реальный запрос OpenRouter на вымышленной тренировке: получен полный валидный JSON на русском языке. Обязательный ZDR отключён с разрешения владельца; запрет сбора данных и платных моделей сохранён. Лимит ответа — 3000 токенов. Опубликованная версия пока не содержит раздела «Разбор».
